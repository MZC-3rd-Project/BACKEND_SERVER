DonMoa는 게이트웨이와 여러 도메인 서비스로 나뉜 마이크로서비스 구조이기 때문에, 장애가 발생했을 때 단순히 로그 몇 줄만 보는 방식으
로는 원인을 빠르게 찾기 어렵습니다. 실제 운영에서는 어떤 요청이 어느 서비스까지 갔는지, 어디서 느려졌는지, 어느 구간에서 에러가 발생했는지를 한 번에 좁혀야 대응 속도가 나옵니다.
그래서 저희는 메트릭, 로그, 트레이스를 각각 따로 보는 것이 아니라, 하나의 요청 흐름으로 연결해서 볼 수 있는 구조로 설계했습니다.

장표를 왼쪽부터 보시면 먼저 신호가 발생하는 지점이 있습니다.
Spring 서비스에서는 JSON 로그를 출력하고, 그 안에 requestId, traceId, spanId 같은 상관관계 키를 같이 남깁니다. 또 Spring Boot Actuator를 통해 /actuator/prometheus 엔드포인트로 애
플리케이션 메트릭을 노출합니다. 여기에 ingress 역할을 하는 nginx도 일반 텍스트 로그가 아니라 JSON access log로 맞춰서 request_id, 상태 코드, 경로, latency 같은 값을 구조화해서 남
기도록 했습니다. 즉, 요청이 처음 들어오는 지점부터 서비스 내부까지 같은 기준으로 추적 가능한 데이터를 남기도록 한 것입니다.

여기서 tracing은 깊게 설명하기보다는, 요청 흐름을 이어주는 연결 장치라고 보시면 됩니다.
저희는 tracing 모듈을 통해 traceId와 spanId를 MDC에 주입하고, 그 값이 애플리케이션 JSON 로그에도 같이 남도록 했습니다. 그래서 로그를 볼 때도 단순히 메시지만 보는 게 아니라, 같은
요청 문맥 안에서 이어서 추적할 수 있습니다. 이게 중요한 이유는, tracing 화면과 로그 화면을 따로 보는 게 아니라, 로그 자체가 이미 요청 흐름을 설명해주는 형태가 되기 때문입니다.

이제 가운데를 보시면, 이 신호들을 실제로 수집하고 저장하는 구간입니다.
메트릭 쪽은 ServiceMonitor가 각 서비스의 /actuator/prometheus 엔드포인트를 30초 주기로 scrape하고, Prometheus가 이 데이터를 저장하고 집계합니다. 그래서 운영자는 Grafana에서 QPS,
에러율, p95, 리소스 사용량 같은 지표를 바로 확인할 수 있습니다.
로그 쪽은 Grafana Alloy가 Kubernetes Pod 로그를 수집해서 Loki로 전송합니다. Loki는 로그 저장과 검색을 담당하고, 단순히 보관만 하는 게 아니라 구조화된 필드 기준으로 검색할 수 있게
해줍니다. 그리고 Loki 저장소는 S3와 IRSA를 이용해서 운영 환경에 맞게 연결했습니다.
Zipkin은 이 장표에 같이 보이는데, 이건 메인 운영 화면이라기보다는 로컬에서 trace가 실제로 잘 생성되고 이어지는지 검증하는 용도로 사용했습니다.

오른쪽은 운영자가 실제로 활용하는 영역입니다.
Grafana에서는 Prometheus 기반 메트릭 대시보드를 통해  지표를 볼 수 있고, Loki 기반 로그 탐색에서는 서비스별 로그, 에러 로그, 특정 요청 흐름을
조회할 수 있습니다. 여기서 핵심은 trace를 별도로만 보는 게 아니라, 로그 안에 이미 requestId와 traceId가 들어 있어서 한 요청 단위로 문제를 추적할 수 있다는 점입니다.

즉 실제 장애 대응 흐름은 이렇게 됩니다.
먼저 메트릭에서 평소보다 p95가 튀거나 에러율이 올라간 걸 봅니다. 그다음 바로 같은 시간대의 로그를 조회해서 어떤 서비스에서 문제가 났는지 확인합니다. 그리고 로그 안에 들어 있는
requestId나 traceId를 기준으로 같은 요청 흐름을 따라가면서 원인을 더 좁힙니다.
이렇게 메트릭에서 이상 징후를 보고, 로그로 들어가고, 다시 요청 단위 상관관계로 원인을 좁히는 흐름이 한 번에 이어진다는 점이 이 장표의 핵심입니다.”

실제 로그 포맷과 적용 근거

“앞 장에서 전체 구조를 설명드렸다면, 이 장은 그 구조가 실제로 어떤 로그 포맷으로 남고, 어떤 설정 파일에 반영돼 있는지를 보여주는 장표입니다.

먼저 왼쪽은 애플리케이션 로그 예시입니다.
여기 보시면 timestamp, service.name, deployment.environment, log.type, level, logger, message 같은 기본 필드가 있고, 그 아래에 requestId, traceId, spanId가 같이 들어 있습니다.
이게 중요한 이유는, 서비스 로그가 그냥 사람이 읽는 문자열이 아니라 검색 가능한 JSON으로 남고, 동시에 어떤 서비스에서 어떤 요청으로 발생한 로그인지 바로 식별할 수 있기 때문입니다.
운영에서는 단순히 “에러가 났다”보다, “어느 서비스의 어떤 요청에서 문제가 났다”까지 이어서 볼 수 있어야 실제 대응이 빨라지는데, 이 포맷이 그 기반이 됩니다.

오른쪽은 nginx access log 예시입니다.
여기도 JSON으로 통일했고, ingress 단계에서도 request_id, trace_id, uri, status, request_time, upstream_response_time 같은 값이 구조화돼 있습니다. 이 부분도 중요한데, 서비스 내부
로그만 보는 것이 아니라 요청이 들어온 첫 진입점부터 같은 키로 따라갈 수 있기 때문입니다.
즉, nginx에서부터 지연이 있었는지, upstream 응답이 늦었는지, 아니면 내부 서비스 처리에서 에러가 난 건지를 더 빨리 나눠서 볼 수 있습니다.

아래쪽은 이 포맷이 실제로 어디에 반영돼 있는지를 보여줍니다.
logback-spring.xml에서는 공통 필드와 MDC 값을 포함해서 앱 로그를 JSON stdout으로 출력하도록 설정했습니다. 그래서 서비스명, 환경, requestId, traceId 같은 값이 실제 로그에 자동으로
들어갑니다.
edge-nginx.yaml에서는 JSON 로그 포맷을 정의하고, X-Request-Id 같은 헤더를 전달해서 ingress와 애플리케이션 로그가 서로 이어질 수 있게 했습니다.
또 alloy-values.yaml에서는 Kubernetes Pod 로그를 수집해서 Loki로 전송하고, grafana-donmoa-alert-rules.yaml에서는 5xx spike나 error burst 같은 로그 기반 이상 징후를 감지하도록 연결
했습니다.

즉, 이 장표의 핵심 메시지는 하나입니다.
저희는 로깅 표준을 문서로만 정리한 게 아니라, 실제 로그 포맷, 수집기, 저장소, 알림 규칙까지 연결해서 운영 가능한 형태로 반영했다는 점입니다. 그래서 지금 DonMoa의 옵저빌리티는 단순
히 로그를 쌓아두는 수준이 아니라, 검색이 가능하고, 요청 상관관계를 추적할 수 있고, 이상 징후는 자동으로 감지할 수 있는 상태라고 말씀드릴 수 있습니다.”

두 장 연결 마무리
“정리하면, 첫 번째 장은 메트릭, 로그, 트레이스가 어디서 발생하고 어디로 수집되고 어디서 활용되는지를 보여주는 구조도이고, 두 번째 장은 그 구조가 실제 코드와 설정에 어떻게 반영됐는
지를 보여주는 근거 장표입니다.
결국 저희가 만든 옵저빌리티는 보기 좋은 대시보드를 만드는 데 목적이 있는 것이 아니라, 장애 상황에서 어디서 문제가 났는지를 더 빨리 찾고 더 빨리 대응할 수 있도록 만든 운영 플랫폼이
라고 보시면 됩니다.”
