# Search 발표 자료

장표 파일: [donmoa-search-presentation.drawio](./donmoa-search-presentation.drawio)

## 발표 흐름 한 줄 요약

우리가 Search에서 하려던 것 -> 그걸 위해 Elasticsearch를 어떻게 세팅했는지 -> 그걸 위해 어떤 색인 구조를 만들었는지 -> 그래서 어떤 기능이 가능해졌는지

## 슬라이드 진행 순서에 맞춘 발표 대사 상세 버전

### 1번 슬라이드 보여주고

첫 번째 슬라이드는 우리가 Search에서 하려던 것이 무엇이었는지를 설명하는 장표입니다.
우리가 만들고 싶었던 것은 단순히 "상품 제목 검색" 하나가 아니라,
사용자가 통합 검색을 할 수 있고,
자동완성까지 받을 수 있고,
상품 정보가 바뀌면 검색 결과도 같이 따라오고,
운영 중 문제가 생기면 색인을 복구할 수 있고,
나중에는 AI enrichment와 검색 분석까지 확장할 수 있는 검색 서브시스템이었습니다.

즉, Search 서비스는 조회 API 하나를 위한 모듈이 아니라,
검색 문서를 만들고 유지하고 운영하는 전체 계층을 목표로 설계한 것입니다.
이 슬라이드의 각 카드들은 그 목표를 기능 관점에서 정리한 것입니다.

정리하면 1번 슬라이드의 핵심은
"우리는 단순 조회 API가 아니라, 검색 경험 전체를 책임지는 Search 서비스를 만들려고 했다"입니다.

### 2번 슬라이드 보여주고

두 번째 슬라이드는 그 목표를 위해 Elasticsearch를 어떻게 세팅했는지를 설명합니다.
먼저 왼쪽을 보시면
인덱스 주소와 이름은 설정 파일에서 관리합니다.
즉, 어디에 붙을지와 어떤 인덱스를 쓸지는 코드에 박아 넣지 않고 설정으로 바꿀 수 있게 했습니다.

가운데를 보시면
인덱스는 외부에서 수동으로만 관리하는 게 아니라,
서비스 안에서 존재 여부를 확인하고 필요하면 직접 생성할 수 있게 해뒀습니다.
이 말은 운영 환경에서 인덱스를 다시 만들거나 초기화할 때도
서비스 코드 기준으로 일관되게 관리할 수 있다는 뜻입니다.

오른쪽을 보시면
한글 검색을 위해 nori analyzer를 사용하고,
검색용 text 필드와 exact match용 keyword 필드를 함께 두는 구조를 만들었습니다.
그리고 아래 문서 모델을 보면
단순 제목만 넣는 게 아니라,
카테고리, 스토어, 태그, 상세 설명, 재고, 펀딩 상태, AI enrichment 필드까지 같이 넣었습니다.

즉, 2번 슬라이드의 핵심은
"우리가 원하는 검색 경험을 만들기 위해,
Elasticsearch를 단순 저장소가 아니라 한글 검색과 풍부한 문서 모델 기준으로 세팅했다"입니다.

### 3번 슬라이드 보여주고

세 번째 슬라이드는 그 목표를 위해 어떤 색인 구조를 만들었는지를 설명합니다.
왼쪽을 보시면
상품, 재고, 스토어 서비스에서 이벤트가 들어옵니다.
우리는 검색 문서를 DB에서 매번 즉시 join 해서 만드는 대신,
이벤트를 받아서 검색 문서를 계속 갱신하는 구조를 택했습니다.

가운데를 보시면
Search 서비스 안에는 이벤트를 받는 계층과,
이 이벤트가 어떤 의미인지 해석하는 계층이 분리되어 있습니다.
즉, 상품이 생성됐는지, 수정됐는지, 재고가 바뀌었는지에 따라
색인을 새로 만들지, 일부를 업데이트할지, 지울지를 결정합니다.

오른쪽을 보시면
여기서 바로 Elasticsearch에 쓰는 것이 아니라,
상품, 재고, 스토어, 펀딩 정보를 다시 읽어서 최종 검색 문서를 구성합니다.
이 구조를 택한 이유는,
이벤트 페이로드 하나만으로는 검색에 필요한 모든 정보를 다 갖기 어렵기 때문입니다.
그래서 검색 문서는 여러 도메인 정보를 다시 조합해서 만드는 방식으로 설계했습니다.

즉, 3번 슬라이드의 핵심은
"우리는 이벤트를 받아 최종 검색 문서를 다시 조합하는 색인 파이프라인을 만들었다"입니다.

### 4번 슬라이드 보여주고

네 번째 슬라이드는 그래서 실제로 무엇이 가능해졌는지를 보여주는 장표입니다.
먼저 왼쪽 위를 보시면
사용자는 통합 검색 API로 키워드, 카테고리, 가격, 상태, 정렬 조건을 함께 사용할 수 있습니다.
즉, 단순 문자열 검색이 아니라 실제 서비스 수준의 필터링과 정렬이 가능한 검색이 됩니다.

오른쪽 위를 보시면
자동완성도 title, tag, store, category 기준으로 제공할 수 있습니다.
즉, 사용자가 입력하는 순간 바로 검색 의도를 유도하는 UX까지 가능해집니다.

왼쪽 아래를 보시면
운영자가 재색인 API를 통해 인덱스를 다시 만들거나 복구할 수 있습니다.
즉, 이벤트 누락이나 스키마 변경이 있어도 검색 인덱스를 다시 회복할 수 있습니다.

오른쪽 아래를 보시면
문서가 색인된 이후에는 AI enrichment 작업을 붙이거나,
검색 실행 / 클릭 이벤트를 분석용으로 활용할 수도 있습니다.
즉, 검색 기능 자체를 넘어
추천, 요약, 태그 보강, 분석 같은 확장 기능으로도 이어질 수 있습니다.

그래서 4번 슬라이드의 핵심은
"이런 세팅과 색인 구조를 만들었기 때문에,
통합 검색, 자동완성, 운영 복구, AI/분석 확장까지 가능해졌다"입니다.

### 마무리 멘트

정리하면,
우리가 Search에서 하려던 것은 단순 조회 API가 아니라 검색 경험 전체를 책임지는 서브시스템을 만드는 것이었습니다.
그걸 위해 Elasticsearch를 코드 안에서 제어 가능한 형태로 세팅하고,
이벤트 기반 색인 파이프라인을 통해 여러 도메인 정보를 다시 조합하는 구조를 만들었습니다.
그래서 지금은 통합 검색, 자동완성, 운영 재색인, AI enrichment, 분석 확장까지 가능한 구조가 됐다고 설명하시면 됩니다.

## 짧은 발표 버전

우리는 Search에서 단순 조회 API가 아니라 검색 경험 전체를 만들고 싶었습니다.
그걸 위해 Elasticsearch를 한글 검색과 풍부한 문서 모델 기준으로 세팅했고,
이벤트 기반 색인 파이프라인으로 여러 도메인 정보를 다시 조합하는 구조를 만들었습니다.
그래서 지금은 통합 검색, 자동완성, 운영 복구, AI enrichment 같은 확장까지 가능한 검색 서브시스템이 되었습니다.

## 발표자 메모

- 이 발표는 코드 이름보다 "우리가 하려던 것"을 먼저 앞에 둔다.
- `SearchOpsController`는 장표에서 "내부 운영용 재색인 API"라고 설명하면 된다.
- 반복 메시지는 "검색은 조회 API가 아니라 문서 기반 서브시스템"으로 잡으면 좋다.
